# Data Records guide

The Data Records section is the most information-dense part of a descriptor and
the one reusers depend on most. It has up to four parts. The first two are
essentially universal (present in ~90%+ of the EBRAINS corpus); the last two are
conditional but common (each ~20–30%).

## 1. Directory tree (required)

Render the structure as a fenced code block rooted at `/ repository-root`, with
an inline `[description]` after each entry. Collapse repeating patterns into
placeholders (e.g. `sub-XX/ses-YY/...`). List the descriptor PDF itself and any
`license.pdf` as records — the real descriptors do (~30% of the corpus).

```
/ repository-root
  data-descriptor.pdf            [this file — EBRAINS data descriptor]
  license.pdf                    [CC-BY-4.0 license]
  sub-XX/                        [one folder per subject]
    ses-YY/                      [one folder per session]
      func/sub-XX_ses-YY_task-ZZZ_bold.nii.gz   [task fMRI volume]
```

## 2. Format table (required)

Follow the tree with a table using the corpus-standard header
**`Format | Extension | Software used / file specification`**. The third column
is a rich free-text field — it should carry, as applicable: the producing
software or script (e.g. *"generated by make_table.py"*), whether the format is
a **standard (BIDS) or "self made"**, units, and naming-convention expansions
(e.g. *"pa = posterior-anterior phase encoding"*).

| Format | Extension | Software used / file specification |
|--------|-----------|------------------------------------|
| Gzipped NIfTI-1 Image | `.nii.gz` | Neuroimaging volume; BIDS. `pa`=posterior-anterior |
| Tab-Separated Values | `.tsv` | BIDS. `participants.tsv` columns `{participant_id, age, sex}` |
| JavaScript Object Notation | `.json` | BIDS sidecar; keys `{path, subject, modality, task}` |

Fill Format and Software columns from `reference/file-formats.md`. For unknown
extensions, ask the user for the format name and producing software.

## 3. Filename-code legend (conditional — when filenames encode metadata)

If filenames or folders encode metadata through a naming scheme, define every
token. This covers BIDS placeholders *and* custom schemes. State each code and
its meaning, e.g. *"`mouseXXX_[age]_[sex]_[stain]`: where `[stain]` is the IHC
marker"* or *"`DXR`, where `X` is the receptor subtype (1 or 2)"*. Without the
legend the tree is ambiguous. See `examples/ephys-custom-naming-pci.md` for a
real custom scheme.

## 4. Container-file contents (conditional — when data sits inside container files)

When data is packaged in container files (`.mat`, `.npz`, `.json`, HDF5/`.nwb`)
rather than one-file-per-measurement, document the *internal* structure, not just
the file. Use a table of the variables/fields/keys the container holds:

| Variable / field | Type | Description | Notes |
|------------------|------|-------------|-------|
| `allEvents` | 3×1 cell | Event timestamps (ms) per trial | one cell per condition |
| `choice` | 3×1 cell | Selection made (-1 left, 0 none, 1 right) | |

Prompt for this whenever the user's formats include a container type. See
`examples/container-mat-decision.md` for a real per-variable table.
