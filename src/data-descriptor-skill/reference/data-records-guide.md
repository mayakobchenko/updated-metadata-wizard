# Data Records guide

Data Records is the section reusers depend on most, and the one that must be
derived from the deposit rather than written from memory. The tree, the counts
and the extensions come from the file listing; the container contents and units
come from sampled files where files may be opened. The author confirms and
annotates. See `listing-and-sampling.md` for how the inputs are obtained.

The section has up to four parts. The first two are present in almost every
EBRAINS descriptor; the last two apply when filenames encode metadata and when
data sits inside container files.

## 1. Directory tree (required)

Render the structure as a fenced code block rooted at `/ repository-root`, with
an inline `[description]` after each entry. Collapse repeating siblings into
placeholders (`sub-XX/`). Every path in the tree exists in the listing, and
every file in the listing is covered by the tree.

```
/ repository-root
  data-descriptor.pdf            [dataset-level: this descriptor]
  Licence-CC-BY.pdf              [dataset-level: licence]
  participants.tsv               [dataset-level: one row per subject]
  sub-XX/                        [one folder per subject, 19 subjects]
    ses-YY/                      [one folder per session, 42 sessions]
      sub-XX_ses-YY_scans.tsv    [session-level: one row per run below]
      meg/
        sub-XX_ses-YY_task-ZZZ_run-R_meg.fif   [per run: raw MEG]
```

Rules the tree follows:

- **Each file kind names its owner.** `[session-level]`, `[per run]`,
  `[dataset-level]`. A file beside sub-entity folders belongs to the enclosing
  entity, and a reader cannot tell that from the name.
- **Dataset-level files are listed**, labelled as belonging to no subject or
  session: descriptor, licence, tables, `README`, `code/`, `docs/`.
- **Depth is literal.** A per-variable file in a subfolder of the session
  folder is shown in that subfolder.
- **Counts are numbers.** "3 planes per recording", "20–25 trials per session",
  not "planes" or "trials".
- **Optional levels and tokens say when they are present and what their absence
  means.** "`ses-` is present only for subjects recorded on more than one day."
  "`run-` absent means run 1."
- **Variants are stated per subject.** "Rat 24101: Neuralynx (`VT1.nvt`,
  `TT<N>.ntt`). Rats 24102–24105: Axona (`<date>.set`, `<date>.pos`)."
- **A name that recurs under several folders is explained.** "`28229_3` under
  `lt/` and under `of/` are two sessions of one recording period, split by
  task."

## 2. Format table (required)

Follow the tree with a table using the corpus-standard header
**`Format | Extension | Software used / file specification`**. One row per
extension in the listing, and no row without an extension in the listing. The
third column carries, as applicable: the producing software or script
(*"generated by make_table.py"*), whether the format is a **standard (BIDS,
NWB) or self made**, the stored unit and any conversion, and naming-convention
expansions (*"pa = posterior-anterior phase encoding"*).

| Format | Extension | Software used / file specification |
|--------|-----------|------------------------------------|
| Neurodata Without Borders | `.nwb` | NWB 2.6, written with PyNWB 2.5. Position in `processing/behavior` stored in cm with `conversion = 0.01` to the declared unit `meters`; apply it. Opened with PyNWB 2.6 and MatNWB 2.7 |
| Tab-Separated Values | `.tsv` | BIDS. `participants.tsv` columns `{participant_id, age, sex}`; age in years |
| JavaScript Object Notation | `.json` | BIDS sidecar; keys `{path, subject, modality, task}` |

Fill Format and Software from `file-formats.md`, then confirm the producing
software with the author. For an unknown extension, ask.

## 3. Filename-code legend (when filenames encode metadata)

Define every token in the naming scheme. Each entry gives:

- the token and its meaning (*"`[stain]` is the IHC marker"*);
- whether it is optional and what its absence means;
- its width and padding (*"`00001`, five digits, zero-padded"*);
- for dates and times, the exact format, including month names
  (*"`2020-Nov-04` is `yyyy-MMM-dd` with English three-letter months; these
  names do not sort chronologically"*);
- ranges and lists inside one token (*"`c9_11` is cells 9 to 11; each cell also
  has a folder of its own"*);
- metadata carried in the names of member files rather than folders (*"the frame
  count is in the `.mmap` name: `_frames_N_`"*).

Without the legend the tree is ambiguous. See `examples/ephys-custom-naming-pci.md`
for a real custom scheme.

## 4. Container-file contents (when data sits inside container files)

For `.mat`, `.npz`, `.json`, HDF5 and NWB, document the internal structure,
from sampled files where files may be opened. Use a table of the variables,
fields or keys the container holds:

| Variable / field | Type | Description | Notes |
|------------------|------|-------------|-------|
| `allEvents` | 3×1 cell | Event timestamps (ms) per trial | one cell per condition |
| `choice` | 3×1 cell | Selection made (−1 left, 0 none, 1 right) | −1/0/1 are the only values |
| `units/spike_times` | float64 (N,) | Spike times, s | NWB; indexed by `units/spike_times_index` |

Rules:

- **Every quantity gives its stored unit and any conversion.** A series stored
  in centimetres and declared in metres is documented as both, with the factor.
- **Reserved values are listed** where they occur: a code for a blank trial, a
  sentinel for a missing response, `NaN` for dropped frames.
- **Where the structure differs between files of one kind, say so**, with the
  count on each side: "`ResponseSomaElectrode` is a `VoltageClampSeries` in 128
  files and a `CurrentClampSeries` in 45; the holding potential is in
  `session_description`."
- **Where files could not be opened**, the table is the author's statement, and
  the validation summary says so.

See `examples/container-mat-decision.md` for a real per-variable table.
